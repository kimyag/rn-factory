# App-owned native modules

Create a native module only when an app needs a native API that Expo and the
shared packages do not provide. Keep app-specific behavior in the app and its
native implementation under `apps/<app>/modules/<module>/`. If more than one
app needs the same module, move it to a shared workspace package.

From the app directory, run the Expo Modules API scaffolder:

```sh
cd apps/<app>
pnpm create expo-module --local
```

Choose a module name and accept the local-module defaults. Expo creates the
module's TypeScript interface, `expo-module.config.json`, and native source
folders under `modules/<module>/`. Import the JavaScript interface from the
app's feature code. Expo Autolinking discovers modules in `./modules`; no app
level native project edits are needed. `pnpm new-app` creates this directory
for every app.

The app-level `ios/` and `android/` directories are generated by CNG and remain
untracked. Local modules may own `ios/` and `android/` directories under
`modules/<module>/`; EAS runs CNG and compiles these module sources as part of
the app build. Run EAS commands from `apps/<app>`. After changing native module
code, install a new development or preview build: an OTA update cannot add or
change native code.

CI typechecks and lints the workspace, checks that `pnpm new-app` copies the
module directory, and runs Expo Autolinking resolution for Android and Apple
platforms in every app. These checks catch malformed module metadata and
unresolvable native source paths without generating app-level native projects.
They do not compile Kotlin or Swift or verify behavior on a device; an EAS
development build and a device smoke check cover those steps.
